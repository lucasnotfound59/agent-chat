# Agent Chat 第二期设计：MCP 接入，让干活中的 agent 进来问别人

日期：2026-11-12
状态：待用户审阅
前置：第一期后端（`2026-11-11-agent-chat-phase1-design.md`）已合并到 main

## 1. 目标

用户在 Codex、Claude Code、OpenCode、DSH 各自的软件里干活时，那个正在干活的 agent 遇到不懂的问题，可以直接向聊天软件里的另一个 agent 提问并拿到回答，然后继续干活。整个软件不需要任何 API key，所有 agent 都走用户已有的登录。

例子：正在某个项目里干活的 Codex 调用工具"问 Claude Code：这个并发问题应该怎么设计？"，一两分钟内拿到 Claude 的回答；这段问答同时留在聊天记录里，用户能看到。

## 2. 范围

本期做：

1. 中枢的"提问"通道：一个 agent 向另一个 agent 提问并同步等到回答。
2. 一个独立的 MCP server（本地小程序），各软件登记一条命令即可接入。
3. 一键登记脚本，把 MCP server 登记到检测到的各个软件里。
4. 点名模型改为走已登录的 agent，移除需要 API key 的实现。
5. 访问令牌改存 macOS 钥匙串。
6. 聊天时不加载各 harness 里用户配置的 MCP 服务、插件和连接器（“按 agent 打开”的开关推迟到界面那一期）。

本期不做：网页界面；干活中的 agent 向群聊发言或读取聊天记录；向人类提问并等人类回答；别人主动找到某个正在干活的会话；拾潮；打包。

## 3. 已确定的产品决定

- 提问是同步的：工具调用一直等到对方答完才返回。
- 提问者的身份就是该 agent 本人：干活中的 Codex 和聊天里的 Codex 是同一个联系人，消息上带"来自工作会话"的标记。
- 接入形态是一个 MCP server，由各软件自己启动（stdio 方式）。
- 整个软件不使用任何 API key。
- 访问令牌存钥匙串；聊天时 MCP 关闭（按 agent 打开的开关在界面那一期做）；每日唤起上限对所有会话生效。

## 4. 架构

新增一个包，中枢增加一条通道，其余沿用第一期。

```
packages/
  adapters/   每个适配器新增"一次性原始提问"能力；聊天时关闭 MCP
  hub/        新增提问通道、成员列表接口、钥匙串令牌、agent 点名
  mcp/        新增：MCP server 小程序 + 登记脚本
```

### 4.1 提问通道（hub）

**会话类型**：新增第三种会话 `ask`，每一对"提问者 → 回答者"一个，标题形如 `Codex → Claude Code`。调度器完全不处理这种会话：不合并等待、不点名、不产生后续轮次。人类可以读，本期不能往里发言。

**接口**：`POST /api/ask`，请求体 `{ as, to, question }`。

- `as`：提问者的适配器名，必须对应一个 agent 成员。
- `to`：回答者，成员名或适配器名，必须是 agent，不能是提问者自己。
- 成功返回 `{ reply, conversationId }`。
- 另有 `GET /api/members` 返回成员列表（名字、自我介绍、是否可用及原因）。

**一次提问的流动**：

1. 找到或创建这一对的 `ask` 会话。
2. 把问题存为提问者的一条消息，标记 `meta.via = "mcp"`，推送事件。
3. 直接唤起回答者的适配器（只读、聊天用的工作目录、该会话对应的 harness 会话），不经过调度器的轮次。
4. 把回答存为回答者的一条消息，推送事件，返回给调用方。

回答者在同一个 `ask` 会话里保留上下文，所以同一个提问者的追问它记得前文。不同项目里的 Codex 会话共用这一个会话，因此工具说明里要求提问自带必要背景。

**约束**：

- 同一个 `ask` 会话里的提问排队逐个处理。
- 每日唤起上限照常适用。
- 全局停止时拒绝新的提问，并中止进行中的提问。
- 调用方断开连接时，中止对应的唤起，不白花额度。
- 回答超时沿用会话的超时设置（默认 300 秒）。

**出错时返回给调用方的内容**（都是一句能让提问的 agent 看懂并继续干活的话）：

| 情况 | HTTP | 说明 |
|---|---|---|
| 回答者不可用（没装、没登录） | 409 | 带原因 |
| 中枢已全局停止 | 503 | |
| 达到每日上限 | 429 | |
| 回答者超时或出错 | 504 / 502 | 会话里同时留一条系统消息 |
| `as` 或 `to` 无效、问自己、问人类 | 400 | |

### 4.2 MCP server（packages/mcp）

一个由各软件启动的本地程序，通过标准输入输出说 MCP 协议，内部通过 HTTP 调中枢。

- 启动参数 `--as <适配器名>` 声明"我代表谁"。
- 令牌由它自己从钥匙串读取，不写进任何软件的配置。
- 中枢地址默认 `http://127.0.0.1:4317`，可用环境变量 `AGENTCHAT_PORT` 改端口。

工具：

| 工具 | 参数 | 返回 |
|---|---|---|
| `list_members` | 无 | 可以提问的成员：名字、擅长什么、当前是否可用 |
| `ask` | `to`、`question` | 对方的回答文本 |

工具说明里写明：什么时候该用（卡住、需要另一个模型的看法或复核）、提问要自带背景、一次调用可能要等一两分钟。

中枢没启动或连不上时，工具立即返回一句明确的提示，不挂起。

**防止套娃**：聊天里被中枢唤起的 agent 不应该再拿到这些工具。两层保证：

1. 聊天时关闭 MCP（见 4.5），所以被唤起的 agent 根本看不到这个 server。
2. 中枢唤起子进程时设置环境变量 `AGENTCHAT_INVOCATION=1`；MCP server 启动时若发现这个变量，就不提供任何工具。

### 4.3 登记脚本

`npm run connect`：检测本机装了哪些软件，列出将要执行的登记命令，确认后执行。`npm run disconnect` 撤销。

- 登记用各软件自己的命令（`codex mcp add`、`claude mcp add`、`opencode mcp add --global`；DSH 通过其配置补丁）。
- 登记时把该 server 的工具调用超时设到 600 秒，保证"等回答"不被软件自己的超时打断。
- 脚本只增删名为 `agent-chat` 的这一条，不动用户其他配置。
- 这个脚本会修改用户各软件的配置，只在用户明确运行它时执行。

### 4.4 点名模型改走 agent

- 每个命令行适配器新增一个能力：`complete(prompt)`，用一次性的新会话回答一段原始提示词，不带聊天包装，不续接。
- 群聊点名改为调用某个 agent 的 `complete`，提示词和输出格式沿用第一期（返回 `{"speakers": [...]}`）。
- 配置项 `triageAgent`：适配器名，或 `"off"`。默认自动选第一个可用的，顺序为 DSH、OpenCode、Codex、Claude Code（按响应速度和成本排）。
- 点名调用用独立的工作目录，同样只读。点名失败时仍退化为只有被 @ 才回。
- 删除第一期的 OpenAI 兼容接口实现和 `config.triage`（地址、密钥、型号）。

代价：每轮点名从一次接口调用变成启动一次 harness，群聊每轮多等几秒到十几秒。

### 4.5 聊天时的 MCP 隔离

用户在各 harness 里配置的 MCP 服务运行在 harness 的只读限制之外（例如 Codex 的 computer-use 插件）。因此：

- 聊天时（包括回答提问和点名）不加载任何用户配置的 MCP 服务、插件或账号连接器。
- 本期只做"全部关闭"。"按 agent 打开"的开关推迟到网页界面那一期，和设置页一起做，因为没有界面时没人能用到它，而每个 harness 的"只放行一部分"都要单独研究。
- `agent-chat` 这个 server 在聊天时始终不加载。

各 harness 的关闭方式（2026-11-12 本机实测）：

| harness | 方式 | 状态 |
|---|---|---|
| Claude Code | 已有 `--strict-mcp-config` | 第一期已做 |
| Codex | `--ignore-user-config --disable apps --disable plugins`，新会话和续接都要带 | 已实测：默认情况下聊天里的 Codex 能看到 `mcp__codex_apps__gmail`、`google_drive`、`github` 等连接器；加上这三个参数后报告没有任何 MCP 工具，续接正常。只加 `--ignore-user-config` 不够，按服务逐个 `-c mcp_servers.<名>.enabled=false` 会因插件提供的服务而报错 |
| OpenCode | 工作目录里的只读 agent `agentchat` 的权限规则 | 待实测：登记一个 MCP 服务后确认该 agent 列不出也调不了它的工具 |
| DSH | headless 配置默认没有任何 MCP 服务 | 用户若自己往 headless 配置里加了 MCP 服务，本期不处理，README 里说明 |

判定标准：被唤起的 agent 列不出、也调用不了任何 MCP 工具。

### 4.6 令牌进钥匙串

- 令牌存为钥匙串条目（服务名 `AgentChat`，账户名 `hub-token`），用系统自带的 `security` 命令读写。
- `config.json` 不再保存令牌；已有的令牌在首次启动时迁入钥匙串并从文件中删除。
- 中枢、MCP server、README 里的 curl 用法都从钥匙串取令牌。
- 代码里令牌的读写藏在一个小接口后面，测试用内存实现，不碰真实钥匙串。

**钥匙串的保护范围（2026-11-12 本机用假条目实测）**：

- Codex 的只读沙箱拦截钥匙串访问，读不到。
- DSH 的只读沙箱不拦截：它执行 `security find-generic-password` 能读出条目内容。
- Claude Code 和 OpenCode 在聊天里没有 shell 工具，无从执行该命令。

所以钥匙串挡住了"读文件"这条路，但挡不住 DSH。移除点名密钥之后，令牌是唯一的秘密，泄露的后果限于本机进程能操作中枢。这一点写进 README。

## 5. 对第一期的修改

- 第一期 §5.4（点名模型）整节由本文 §4.4 取代：不再有 API 密钥。
- 第一期 §7 的 `config.json`：保存 `triageAgent`、DSH 的模型设置；不含令牌和任何密钥。
- `Conversation.kind` 增加 `ask`。
- `HubEvent` 不变；`ask` 会话的消息照常以 `message` 事件推送。

## 6. 出错处理

除 4.1 的表格外：

| 情况 | 处理 |
|---|---|
| MCP server 连不上中枢 | 工具返回"Agent Chat 中枢没有运行，请先启动"，不重试 |
| 钥匙串里没有令牌 | 同上，并提示先启动一次中枢 |
| MCP server 被中枢唤起的进程加载（套娃） | 不提供任何工具 |
| 登记脚本发现某软件没装 | 跳过并说明 |

## 7. 测试

- 提问通道：用假适配器测排队、上限、停止、断开即中止、各种错误码、调度器不处理 `ask` 会话。
- MCP server：用假的中枢 HTTP 服务测两个工具、连不上时的提示、套娃保护；用 MCP SDK 的客户端在测试里真实走一遍协议。
- 点名：用假适配器的 `complete` 测选择顺序、失败退化、`"off"`。
- 令牌：内存实现测迁移和读取；真实钥匙串只在手动冒烟里碰。
- 各适配器的 MCP 隔离和 `complete`：单元测试测参数；手动冒烟脚本在真实命令行上验证"列不出 MCP 工具"和"能完成一次原始提问"。
- 端到端手动验证：登记后在真实的 Codex 会话里调用 `ask` 问 OpenCode（或 DSH），拿到回答，聊天记录里能看到这段问答。Claude Code 相关的验证取决于其命令行是否已登录。

## 8. 完成标准

- 在至少两个真实软件之间跑通一次"干活中的 agent 提问 → 拿到回答 → 聊天记录可见"。
- 被中枢唤起的 agent 拿不到 `agent-chat` 的工具，也拿不到用户配置的其他 MCP 工具（默认设置下）。
- 整个软件的配置和代码里没有任何 API key；`config.json` 里没有令牌。
- 未 @ 任何人的群聊消息能通过 agent 点名引出回应（至少用一个真实 agent 验证一次）。
- 自动测试全部通过。
