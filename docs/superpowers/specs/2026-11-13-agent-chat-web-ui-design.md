# Agent Chat 网页界面设计（第一期 1b：最小可用版）

日期：2026-11-13
状态：设计已逐节确认，待实施计划

## 1. 目标与范围

第一期分两步：1a 是中枢后端（已完成），1b 是网页界面（本文档）。本文档先做一个能实际使用的最小版，再列出完整版的范围；完整版在最小版完成后单独写实施计划。

最小版做：

- 会话列表：群聊、私聊、agent 互问（ask 会话）三组；私聊显示各 agent 的可用状态。
- 发消息并实时看到回复；Markdown 和代码块；@ 成员（带补全）；正在输入。
- 新建群聊。
- 群聊的暂停开关；全局停止和恢复。
- 在 ask 会话里插话（见 3.3）。
- 重新检查各 agent 的可用状态。
- 跟随系统的浅色和深色模式。

最小版不做：附件、回复某条、未读数、群设置（成员、群名、轮数、上限、超时）、设置页、失败调用的重试按钮、调用记录视图、删除会话。这些列在第 7 节。

## 2. 已确定的产品决定

- 视觉风格：气泡式（类似 iMessage）。人的消息在右侧蓝色气泡；agent 的消息在左侧白色气泡，带头像和名字。agent 气泡最宽占消息区的 85%，代码块在气泡内占满宽度并可横向滚动，以容纳长回答。
- 打开方式：`npm run hub` 启动时自动用默认浏览器打开界面，终端同时打印地址。
- 技术方案：React + Vite，新增 `packages/web`，构建成静态文件，由 hub 在同一端口提供。
- 登录：复用 keychain 里现有的 hub token，不新增登录机制（见 3.1）。
- ask 会话：在侧栏单独分组；人可以在里面发言。

## 3. 架构

### 3.1 进程、端口与登录

- 仍然只有一个 hub 进程、一个端口（默认 4317）。hub 在 `/` 下提供 `packages/web` 的构建产物；`/api/*` 和 `/ws` 不变。
- 静态文件（`index.html` 和构建出的 JS、CSS 等）免鉴权，其中不含任何秘密；`/api/*` 仍要求 `Authorization: Bearer <token>`，`/ws` 仍要求第一条消息是 `{type:"auth", token}`。现有的 Host 头检查对静态文件同样适用。
- 启动时 hub 打印并打开 `http://127.0.0.1:<port>/#token=<token>`。环境变量 `AGENTCHAT_NO_OPEN=1` 时只打印不打开。
- 页面加载时：如果地址的 fragment 里有 `token`，读出后存入 localStorage，并用 `history.replaceState` 把它从地址栏抹掉；否则从 localStorage 读。两处都没有时显示"请用终端里 `npm run hub` 打印的地址打开"。
- 同一个浏览器打开过一次后，直接访问 `http://127.0.0.1:<port>` 即可；hub 重启不需要重新打开，因为 token 不变。
- 没有构建产物时，访问 `/` 返回一页说明"先运行 `npm run build`"，hub 本身照常启动。
- 已知代价（写进 README）：token 存在该浏览器的 localStorage 里；打开浏览器的瞬间 token 出现在 `open` 命令参数里，同机其他进程可以从进程列表看到（与写 keychain 时相同）。

### 3.2 WebSocket 的 Origin 检查

浏览器发起的 `/ws` 连接若带 `Origin` 头，必须等于 hub 自己的地址（`http://127.0.0.1:<port>` 或 `http://localhost:<port>`），否则在握手时拒绝。不带 `Origin` 的连接（脚本、测试）不受影响，照旧靠 token 鉴权。

### 3.3 人在 ask 会话里发言

- 人通过现有的 `POST /api/conversations/:id/messages` 在 ask 会话里发消息。
- 只有人发的消息会触发回答：hub 唤起被问方（会话的 `ask_to` 成员），不经过 triage；agent 发的消息不触发任何调用，所以不会循环。
- 实现上复用 MCP 提问已有的 ask 队列（`Scheduler.invokeForAsk`）：同一个 ask 会话里的插话和 MCP 提问依次排队，不会同时调用被问方；遵守全局停止，以及该 ask 会话自己的每日上限和超时设置；唤起记录的 `reason` 为 `ask`。
- 被问方在自己原来的 harness 会话里继续（沿用现有的会话续接），看到的上下文包括之前的问答和人的插话。人不是 ask 会话的成员，所以提示词里发言人的名字要按全部成员查找，否则人的插话会显示成"系统"。
- 超时和出错照旧由 hub 写成系统消息；因全局停止、到达上限、被问方不开口或被中止而没有回答时，也写一条系统消息说明原因。最小版界面不提供 ask 会话的暂停开关。
- 提问方的 `ask` 调用早已返回，看不到插话；它下次向同一成员提问时，被问方看得到完整历史。
- 通过 `/api/ask` 进来的提问照旧由 AskService 处理，不受本改动影响。

### 3.4 停止或暂停时不丢问题（第一期遗留 I3）

现状：回合开始时就把触发消息标记为已处理，回合被停止或暂停打断后，恢复时那条问题不再有人回答。

改为：回合被打断（停止或暂停）且该回合里没有任何 agent 完成回答时，把"已处理到的位置"恢复成回合开始前的值，恢复后重新处理；已经有 agent 回答完的回合不回滚，避免同一个 agent 重复回答。

### 3.5 可用状态刷新

- 新增 `POST /api/availability/refresh`：重新检查所有 adapter，返回最新的可用状态。
- 任一 agent 的可用状态变化时，通过 WebSocket 推送 `{type:"availability", adapter, availability}`。
- 界面左栏底部提供"重新检查可用状态"按钮。

### 3.6 侧栏实时更新

以下情况必须推送 `{type:"conversation", conversation}`（现有代码已经都会推送，补上测试即可）：新建群聊、首次出现 ask 会话、修改会话设置。界面收到后插入或更新侧栏条目。

`/api/state` 返回的每个会话附带 `lastMessage`（最后一条消息，没有则为 `null`），供侧栏显示摘要和按最近活动排序；之后由 `message` 事件更新。

## 4. 界面

### 4.1 布局

- 左栏：顶部标题和"＋ 群聊"；中间三组会话（群聊、私聊、agent 互问）；底部连接状态和"重新检查可用状态"。
  - 群聊和 agent 互问的条目显示最后一条消息的摘要。
  - 私聊条目的头像右下角显示可用状态（可用为绿点，不可用为灰点并在名字旁写原因，如"未登录"）。
  - agent 互问按最近活动时间倒序，标题形如"Codex → OpenCode"。
- 右侧：
  - 头部：会话标题和成员；群聊显示"暂停本群"开关；始终显示"全部停止"，停止后变为"恢复"。
  - 消息区：人的消息、agent 的消息（见第 2 节）、系统消息（超时、出错、上限、停止等，居中灰色小条）、正在输入（对应 agent 头像旁的"●●●"）。
  - 输入框：输入 `@` 弹出成员补全，不可用成员灰显；Enter 发送，Shift+Enter 换行。
- 新建群聊弹窗：填群名、勾选 agent 成员，提交后跳到新群。

### 4.2 代码组织（`packages/web/src`）

每个文件只做一件事：

- `api.ts`：带 token 的 HTTP 请求；`ws.ts`：WebSocket 连接、鉴权、重连。
- `token.ts`：从地址 fragment 或 localStorage 取 token，并抹掉地址里的 token。
- `store.ts`：全部状态（成员、可用状态、会话、各会话已加载的消息、正在输入、全局停止、连接状态），以及处理每种 WebSocket 事件的纯函数。
- 组件：侧栏、会话条目、会话头部、消息列表、单条消息、Markdown 渲染、输入框、@ 补全、新建群聊弹窗、连接状态提示。
- 样式：配色全部用 CSS 变量，`prefers-color-scheme` 切换浅色和深色。

### 4.3 数据流

- 启动：取 token，拉一次 `/api/state`，连接 `/ws`。
- 打开会话：加载最近 50 条消息；向上滚动到顶时用 `beforeSeq` 加载更早的。
- WebSocket 事件按类型更新 store：`message` 追加到对应会话（按 `seq` 去重）并更新侧栏摘要；`typing` 设置或清除正在输入；`conversation` 插入或更新会话；`stopped` 更新全局停止；`availability` 更新可用状态。
- 发消息走 HTTP，消息本身以 WebSocket 推回的为准，界面不自行插入，避免重复。

### 4.4 Markdown 安全

agent 的回答是不可信内容。Markdown 渲染不允许原始 HTML，链接加 `target="_blank" rel="noopener noreferrer"`，不渲染 `javascript:` 等非 http(s) 链接。否则 agent 可以在回答里注入脚本读取 localStorage 里的 token。代码块用语法高亮库渲染，只输出转义后的文本。

## 5. 出错处理

- WebSocket 断开：左栏底部显示"连接中断，正在重连"，按 1、2、4…最长 30 秒的间隔重连；连上后重新拉 `/api/state` 和当前会话的最新消息，按 `seq` 去重补齐。
- 401：整页提示"请用终端里 `npm run hub` 打印的地址重新打开"，并清除 localStorage 里的旧 token。
- hub 没有运行（请求失败或连不上）：显示"hub 没有运行，请在终端运行 `npm run hub`"，定期自动重试。
- 发送失败：输入框内容保留，显示错误原因，可再次发送。
- 新建群聊失败：在弹窗里显示原因。
- agent 的超时、出错、上限由 hub 写成系统消息，界面照常显示。

## 6. 测试

自动测试一律不调用真实 agent CLI、真实网络和真实 keychain，沿用仓库的测试防线（`test/guard.ts`），并给它加上 `open` 的假脚本，防止测试真的打开浏览器。

- 后端（先写失败的 test 再实现）：静态文件免鉴权而 `/api` 仍需 token；没有构建产物时的说明页；`AGENTCHAT_NO_OPEN`；WebSocket 的 Origin 检查；ask 会话里人发言只唤起被问方、agent 消息不触发、遵守停止和上限；I3 回滚规则（无人答完则回滚，有人答完不回滚）；可用状态刷新与推送；各类 `conversation` 事件。
- 前端单元测试（vitest + jsdom）：store 对每种事件的处理（去重、补齐、正在输入的开始和结束）；token 的读取、保存与抹除；Markdown 不执行 HTML、不渲染危险链接；@ 补全的过滤。
- 端到端（Playwright）：用假 adapter 的 hub（临时数据目录、随机端口）在真实浏览器里覆盖：用带 token 的地址打开、私聊发消息看到回复、新建群聊、@ 某个 agent、正在输入、暂停与全部停止、在 ask 会话里插话、断开后重连补齐消息。
- 人工验收：用真实 hub 打开界面，与一个真实 agent 私聊一次（需要先征得用户同意，因为会消耗额度）。

## 8. 验收标准

- `npm run build` 后 `npm run hub` 自动打开浏览器，界面显示四个私聊和各 agent 的可用状态。
- 在私聊里发消息能看到正在输入和回复；在群聊里 @ 某个 agent 只有它回答。
- 新建群聊后侧栏立刻出现；暂停本群和全部停止生效，恢复后被打断的问题会被重新处理。
- agent 之间通过 MCP 提问后，侧栏"agent 互问"里出现对应会话；在其中插话，被问方会回答。
- hub 重启后页面自动重连并补齐消息；同一个浏览器不需要重新打开带 token 的地址。
- 全部自动测试和 typecheck 通过；仓库中不包含任何本机个人信息。
